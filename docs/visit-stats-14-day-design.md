# PostgreSQL 방문 통계: 자료구조와 읽기·쓰기 설계

갱신일: 2026-11-07 · PostgreSQL 구현 · Vercel Marketplace의 Neon Free 연결 기준 · Redis는 사용하지 않음

## 목표

서버 인스턴스별 메모리 Map을 PostgreSQL 공용 저장소로 교체한다. 현재 코드는 한국 날짜가 바뀔 때만 초기화하며 정오 초기화 버그는 재현되지 않았다. 그러나 Vercel 인스턴스가 바뀌거나 종료되면 메모리 집계가 사라질 수 있다.

개별 기기의 중복 확인 기록은 최근 14일만 유지하고, ID가 없는 일별 합계는 장기 보관한다. 최근 14일을 날짜·요일별 UI로 조회한다. 20년 운영 시에도 개별 방문 기록이 계속 쌓이지 않도록 한다.

## 자료구조

### visit_daily_devices: 중복 확인용

| 열 | 타입 | 의미 |
| --- | --- | --- |
| scope | text | 서버가 결정하는 production / preview 등의 환경 구분 |
| day | date | DB 시각으로 계산한 한국 날짜 |
| visitor_id | uuid | 브라우저에 보관한 무작위 ID. 문자열 대신 UUID 타입 사용 |
| category | smallint | 0=아이폰 웹, 1=아이폰 PWA, 2=안드로이드 웹, 3=안드로이드 PWA |

기본키는 `(scope, day, visitor_id)`다. 분류는 기본키에 넣지 않으므로 같은 ID가 그날 다른 접속 방식으로 들어와도 두 번 세지 않는다. category는 그날 첫 등록 값을 유지하며 최근 기록의 합계 검증에도 쓸 수 있다.

날짜가 앞에 오는 기본키 인덱스를 최근 14일 정리에 사용한다. 기기별 장기 이력을 조회하지 않으므로 visitor_id 단독 인덱스는 만들지 않는다.

### visit_daily_counts: 장기 보관용 일별 합계

| 열 | 타입 | 의미 |
| --- | --- | --- |
| scope | text | 환경 구분 |
| day | date | 한국 날짜 |
| ios_web | integer | 아이폰 웹 기기수 |
| ios_pwa | integer | 아이폰 PWA 기기수 |
| android_web | integer | 안드로이드 웹 기기수 |
| android_pwa | integer | 안드로이드 PWA 기기수 |

기본키는 `(scope, day)`다. 네 수치는 NOT NULL, 기본값 0, 음수 금지 제약을 둔다. 전체·OS별·웹/PWA별 합계는 네 수치에서 계산한다. 별도 전체 합계를 저장해 분류 합계와 어긋나게 만들지 않는다.

날짜당 행 하나를 계속 갱신하며, 하루가 지나도 이 행을 삭제하지 않는다.

### visit_stats_state: 환경당 상태 한 행

`scope`를 기본키로 `collection_started_at timestamptz`, `last_cleanup_day date`를 보관한다. 기록 시작 전 날짜를 0으로 오해하지 않게 하고 오래된 중복 확인 기록의 정리를 하루 한 번만 수행하는 데 사용한다.

## 쓰기 패턴

휴대폰의 페이지가 보이는 상태에서 오늘 집계 성공 여부를 확인한다. 아직 성공하지 않은 날만 `POST /api/visit-stats`를 호출한다. 요청 본문은 기존 ID와 접속 방식이며 날짜·환경은 서버가 결정하고 OS는 요청의 브라우저 정보에서 판별한다.

한 DB 트랜잭션에서 다음을 실행한다.

1. DB 시각으로 한국 날짜를 한 번 계산한다. 트랜잭션 내 단계들이 자정 전후 서로 다른 날짜를 쓰지 않게 한다.
2. 상태 행의 조건부 갱신으로 오늘의 정리를 한 요청만 맡는다. 해당 요청만 14일 범위 밖의 중복 확인 행을 삭제한다.
3. 중복 확인 테이블에 `INSERT ... ON CONFLICT DO NOTHING RETURNING ...`으로 등록한다.
4. **3번에서 새로 삽입된 경우만**, 일별 합계 행을 생성하거나 해당 분류 수치를 DB 안에서 1 증가시킨다.
5. 전체를 커밋한 뒤 성공을 응답한다. 중간에 실패하면 중복 확인 등록과 합계 증가를 모두 롤백한다.

`SELECT로 존재 확인 → INSERT`나 `SELECT count → 애플리케이션에서 +1 → UPDATE` 패턴은 쓰지 않는다. 기본키 제약과 충돌 처리, DB 내부 증가 연산을 사용한다.

같은 ID의 동시 요청은 한 요청만 합계를 올린다. 서로 다른 ID는 각각 반영된다. 커밋 후 응답이 유실돼도 같은 ID로 재시도하면 합계가 다시 올라가지 않는다.

브라우저의 오늘 완료 표시는 성공 응답 이후에만 저장한다. 이는 통신량을 줄이는 용도이며 최종 중복 방지 책임은 DB에 둔다. DB를 사용하면 기존 5분 주기 재등록은 제거할 수 있다. 날짜 변경과 오류·오프라인 복구 시에는 다시 확인한다.

## 조회 패턴

`GET /api/visit-stats?days=14`는 오늘과 이전 13일의 일별 합계만 읽는다. `(scope, day)` 인덱스로 최대 14행을 조회하므로, 20년치 기록이 있어도 매번 전체를 읽지 않는다.

서버가 정렬된 14일 응답을 만들고 네 수치에서 전체·OS별·접속 방식별 합계를 계산한다. 중복 확인 테이블과 기기 ID는 화면 조회에 사용하거나 반환하지 않는다.

- 모달 열기·새로고침 때만 조회한다. 날씨 자동 갱신마다 이력을 읽지 않는다.
- 날짜 선택은 이미 받은 14일 응답으로 브라우저에서 처리해 추가 요청을 만들지 않는다.
- 수집 시작 전은 `—`, 수집 시작 이후 방문이 없는 날은 0으로 구분한다. 도입 당일은 일부 시간만 집계됐다고 안내한다.
- DB 조회 실패는 `확인 불가`로 표시하고 0으로 덮어쓰거나 메모리 집계로 자동 전환하지 않는다.
- 같은 DB의 쓰기 결과를 읽는 경로를 사용한다. 초기에는 인스턴스별 합계 캐시를 두지 않는다.
- 이전 PWA의 POST 응답에 필요한 오늘 합계는 등록 커밋 후 별도 SELECT로 읽어 호환을 유지한다.

UI는 최근 14일을 7칸 × 2줄로 표시하며, 각 칸에 날짜·요일·기기수를 넣는다. 기본 선택은 오늘이고 날짜 선택 시 기존 분류별 표가 바뀐다. 사용자 지정 안내 문구와 PWA 표기는 유지한다.

## 보관과 정리

현재 날짜 D에 대해 중복 확인 테이블의 `day < D - 13일`인 행을 하루 한 번 삭제한다. 예를 들어 11월 7일에는 10월 25일부터 11월 7일까지 유지한다. 일별 합계는 삭제하지 않는다.

하루 첫 쓰기 요청에서 DB 상태 행으로 정리를 한 번만 실행한다. 방문이 없으면 새 데이터도 쌓이지 않으므로 이를 위한 별도 유료 스케줄러는 필요 없다. 정리와 통계 쓰기의 DB 잠금 순서를 통일한다.

삭제된 행의 공간은 PostgreSQL autovacuum으로 재사용하게 관리한다. API 원문·ID·요청 로그를 다른 DB 테이블에 무제한 보관하지 않는다.

## 20년 저장량

운영 환경 하나, 하루 100기기 기준:

| 데이터 | 유지되는 행 수 |
| --- | ---: |
| 일별 합계 | 20년 동안 약 7,305행 |
| 중복 확인 | 최근 14일 약 1,400행 |
| 수집·정리 상태 | 1행 |

일별 합계의 주요 값은 날짜와 네 정수다. 인덱스·행 오버헤드·공간 재사용을 포함해 통계 테이블 자체의 용량을 수 MB 수준으로 유지하는 것을 목표로 하고, 구현 시 실제 DB 크기로 확인한다. 서비스 전체 저장 공간이나 향후 무료 요금 정책을 20년간 보장한다는 뜻은 아니다.

구현 검증에서는 PostgreSQL 엔진인 PGlite에 20년치 일별 합계와 최근 14일 × 100기기를 넣고 VACUUM ANALYZE 후 측정했다. 다른 검증 행까지 포함한 테이블·인덱스 합계는 **1,040,384바이트(약 1MB)**였고 최근 14일 조회에 기본키 인덱스 사용을 확인했다. 원격 DB의 버전·공간 재사용 상태 등에 따라 실제 용량은 달라질 수 있다.

최근 14일 합계의 합은 같은 기기를 여러 날짜에 포함할 수 있으므로 `14일 고유 사용자 수`라고 부르지 않는다. 장기 합계는 일별 추이 확인용이며 개별 기기의 장기 이력은 남기지 않는다.

## 구현 검증

1. 한국 정오·자정·월말·연말 날짜 판정.
2. 같은 ID 동시 요청 및 응답 유실 후 재시도 시 한 번만 증가.
3. 합계 갱신 실패 시 중복 확인 등록도 함께 롤백.
4. 서버를 새로 생성해도 같은 DB의 집계 유지.
5. 14일 삭제 경계, 합계 보존, 첫날 동시 정리 요청.
6. 20년치 기록에서도 최근 14일만 인덱스로 조회.
7. 수집 시작 전·방문 없음·DB 장애의 화면 구분.
8. 환경 분리, ID 비노출, 이전 PWA 호환.
