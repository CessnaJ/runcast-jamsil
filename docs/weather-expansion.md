# 위치 선택·주간 예보 구현

## 화면

- 모바일 공통 위치 버튼 → 네이버 지도 중앙 핀. 지도 클릭/이동 중에는 날씨 API를 호출하지 않고 ‘이 위치 사용’로 확정한다.
- 기존 기본 코스 3개, 마지막 확정 위치 자동 저장. 사용자 이름은 30자까지이며 HTML 출력 시 이스케이프한다.
- 지도 오류 시 기본 장소와 좌표 직접 입력을 제공한다. 현재 위치는 버튼을 눌렀을 때만 요청한다.
- 국내 지원 영역은 `assets/weather-domain.mjs`의 보수적인 본토·도서 지역 범위로 검증한다. 정밀 국경/행정구역 판정이나 주소 검색은 아니다. 해외 주요 좌표는 400으로 거절하며, 도서 지원 영역은 필요 시 추가할 수 있다.
- 하단 러닝 / 비구름 / 주간 3탭의 ‘주간’: 오늘 포함 7일, 시간별 기온·강수확률·강수량과 체감·바람·돌풍을 기본 표시하며 체감·바람·돌풍은 접을 수 있다. 날짜와 출발 시간을 고르면 1시간 옷차림만 변경한다. 출발 시간 버튼과 같은 열의 모든 데이터 셀에서 시간을 선택할 수 있으며 키보드는 기존 시간 버튼을 사용한다. 옷차림의 체감온도 비교는 오늘 선택 시 어제 같은 정시, 미래 날짜 선택 시 오늘 같은 정시를 기준으로 하며 어느 쪽이든 자료가 없으면 생략한다.
- 러닝 탭의 지금/오전 6시/오후 8시는 주간 시간 선택과 독립적이다. 러닝 판단은 눈·비와 최근 강수에 따른 노면 상태 기준이며, 결론 카드에는 선택한 출발·복귀 기온(°C)을 강수확률·강수량과 함께 표시한다. 러닝 기온과 주간 기온·체감·옷차림은 같은 위치의 Open-Meteo hourly 스냅샷을 공유한다. 날짜와 시각을 포함한 정시 bucket으로 매칭하고, 정시 사이 시각은 해당 시간대 시작 값을 사용한다.
- 운동 이미지는 추후 추가한다. 빈 이미지 카드를 노출하지 않는다.

## 저장과 TTL

모든 기기 상태는 저장 실패를 허용하는 localStorage 래퍼를 사용한다. 서버에 자동 전달되는 쿠키는 쓰지 않는다.

- `runcast.preferences.v1`: location, comfort(cold/normal/hot). 이전 설정 객체의 관리용 목록 필드는 읽지 않고 다음 저장에서 제외한다. 위치·체감·예보 캐시 키는 보존한다.
- `runcast.cache.core.v1`: 위치별 결론용 원천 조립 결과. 5분 TTL.
- `runcast.cache.weekly.v1`: 위치별 주간 결과. 30분 TTL.
- `runcast.cache.weekly.v1`의 성공 결과는 러닝 화면 기온에도 사용한다. 앱 시작 때 주간 공급자 조회를 시작하고, 같은 위치의 동시 진입·새로고침은 하나의 진행 중 요청을 공유한다. 위치가 바뀌면 이전 응답은 새 위치 상태에 반영하지 않는다.
- 캐시는 각 종류별 최근 10개 위치를 보관한다. TTL은 삭제 시각이 아닌 갱신 시도 시각이다. 조회 실패 시 마지막 결과와 실제 수집 시각을 유지한다.
- `runcast.refresh.v2`에는 자료 종류·위치별 마지막 시도/성공 시각, 다음 가능 시각, 연속 실패 횟수와 서버 재시도 시각만 제한적으로 저장한다. 진행 중 Promise와 잠금은 저장하지 않는다. 정상 주기는 눈·비 5분, 주간·공통 기온 30분이며 실패 재시도는 1·2·4분 뒤, 이후 30분 간격에 작은 jitter를 더한다. 수동 갱신은 자동 backoff를 건너뛸 수 있지만 CCTV는 2초, 그 외는 10초의 최소 간격과 서버 `Retry-After`는 따른다. 브라우저 요청 제한은 기본 30초이고, KMA 예보 뒤 최근 실황·다중모델을 조합하는 core 응답만 기존 공급자 제한을 고려해 45초로 제한한다.
- 보이는 온라인 화면의 진입·앱 복귀(`visibilitychange`, `pageshow`)·온라인 복귀와 기존 매분 검사만 공통 요청 경로를 호출한다. 숨김 상태에는 요청 판단과 레이더 재생 타이머를 멈추며, CCTV는 화면에서 필요할 때만 별도 usable 기간을 확인한다.
- 기존 샘플 캐시와 섞이지 않는 새 저장 키를 쓴다. 샘플 응답은 저장·판정에서 제외한다.
- 브라우저와 설치 PWA의 저장 공간 공유 여부는 플랫폼에 따라 다르며, 기기 간 동기화는 없다. 사이트 데이터 삭제/저장 공간 정리/비공개 모드에서는 보존되지 않을 수 있다.

## API

기존 POST `/api/mobile-forecast`, `/api/mobile-context`, `/api/snapshot`은 `{ "route": "seokchon" }` 요청을 계속 지원한다. 새 요청은 다음과 같다.

```json
{ "location": { "lat": 37.5082, "lon": 127.1001, "name": "석촌호수" } }
```

위치는 공통 resolveLocation()으로 처리한다. 커스텀 좌표 오류를 석촌호수로 조용히 대체하지 않는다. 응답의 기존 route 객체에 정규화된 좌표/id/name을 담는다. 기상청 기존 격자 변환, 레이더 투영은 유지한다. CCTV는 선택 좌표에서 15km 이내, 수도권 고정 공항 참고 자료는 잠실 기준 65km 이내에서만 제공한다.

POST `/api/weekly-forecast`는 같은 위치 계약을 사용한다.

- source: Open-Meteo, timezone: Asia/Seoul.
- daily: date/low/high/code, 7개 날짜.
- hourly: time/temperature/feelsLike/humidity/precipitation/probability/windSpeed/gusts/windDirection/code.
- fetchedAt: 실제 공급자 응답 수집 시각. expiresAt: 수집 시각+30분. 캐시 응답을 재조립해도 수집 시각을 현재로 덮지 않는다.
- 기온 °C, 풍속 m/s, 강수량 mm. Open-Meteo 강수량은 해당 시각 직전 1시간 누적이다. UI는 별도 순수 runningIntervals()로 출발 구간을 만든다. 06시 열의 강수량·강수확률·돌풍은 07시 값을 사용하고, 기온·체감·풍속은 06시 값을 쓴다. 옷차림은 이 모델의 출발·복귀 체감과 풍속, 해당 구간 돌풍을 공유한다. 정확한 복귀 시각이 없으면 null이며 마지막 값을 복제하지 않는다.
- 기온 °C, 풍속 m/s, 강수량 mm. Open-Meteo 강수량은 해당 시각 직전 1시간 누적이다. UI는 별도 순수 runningIntervals()로 출발 구간을 만든다. 06시 열의 강수량·강수확률·돌풍은 07시 값을 사용하고, 기온·체감·풍속은 06시 값을 쓴다. 옷차림은 이 모델의 출발·복귀 체감과 풍속, 해당 구간 돌풍을 공유한다. 정확한 복귀 시각이 없으면 null이며 마지막 값을 복제하지 않는다. 러닝 결론의 기온도 이 hourly 배열에서 날짜·epoch bucket으로 직접 찾고 주간 표와 동일하게 `toFixed(0)` 반올림을 적용한다. 숫자가 아닌 문자열·누락값은 0으로 바꾸지 않는다.
- 공급자에는 8일을 요청하되 7개 날짜만 노출한다. 7일째 23시 출발의 복귀 시각을 위해 8일째 00시가 필요하다.
- 데이터가 없으면 null 또는 오류를 반환하며 0으로 바꾸지 않는다. Open-Meteo 기본 모델 선택을 사용한다. 기존 결론용 2일 다중모델 조회는 독립적이다.
- 주간 조회는 15초 공급자 타임아웃, 원천 메모리 캐시는 30분/오류 시 최대 7일이며 Vercel 인스턴스 간 공유되지 않는다. 브라우저 캐시는 인스턴스 재시작에도 마지막 조회 결과를 유지한다.
- `/api/mobile-forecast`와 `/api/weekly-forecast`는 원천 stale fallback이 사용된 경우 additive `refresh: { stale, retryAt, failed }` 및 `cache.retryAt` 메타를 전달한다. `dataUpdatedAt`/`fetchedAt`는 원래 성공 자료 시각이며 retryAt은 다음 원천 재시도 가능 시각이다. 서버 캐시·stale cooldown은 인스턴스 메모리 범위에서만 보장하며 Redis/DB 기반 전역 rate limit은 제공하지 않는다.
- `/api/mobile-context`의 CCTV 결과도 `cctv.usableUntil`, `cctv.retryAt`, `cctv.stale`을 별도로 가진다. 주간 화면의 주기 검사는 CCTV 요청을 시작하지 않는다.

새 API 키나 주소 검색 서비스 활성화는 필요하지 않다. 기존 네이버 Dynamic Map 공개 ID와 허용 도메인 설정을 재사용한다. 기상청·ITS·API허브 키는 기존 서버 환경변수만 사용한다.

## 러닝 눈·비 판단

러닝 결론은 `assets/weather-domain.mjs`의 `evaluateRunWindow()` 한 곳에서 계산한다. 실제 러닝 모드는 출발·30분·복귀 세 점이 모두 유효해야 하며, 누락·비수치 강수량이나 demo 자료가 하나라도 있으면 `unknown`/`자료가 부족해 판단하기 어려워요`를 반환한다. `makeDecision()`의 기존 단일 점 호출은 호환성을 위해 유지하지만 실제 모드에는 세 점 규칙을 적용한다. 화면의 배지 색, 제목, `reasonCode`, `reason`, 예상 누적·최대값은 같은 결과 객체를 사용한다.

| 우선순위 | 조건 | level / reasonCode | 제목 |
| --- | --- | --- | --- |
| 0 | 자료 없음·demo·불완전한 세 점 | unknown / unavailable | 자료가 부족해 판단하기 어려워요 |
| 1 | 눈·진눈깨비(PTY 2·3·6·7 또는 분석 snow) | red / snow | 눈·진눈깨비가 예상돼요 |
| 2 | 선택한 세 점의 최대 시간당 강수량 ≥ 3mm 또는 1시간 누적 ≥ 3mm | red / rain_heavy | 비가 많아 러닝을 미루는 게 좋아요 |
| 3 | 신뢰 가능한 남·남서·서쪽 접근 CCTV의 현재 비가 2곳 이상 / 1곳 | red·yellow / cctv_rain | 주변 CCTV에 비가 보여요 |
| 4 | 최대 시간당 강수량 ≥ 1mm 또는 누적 ≥ 1mm | yellow / rain | 비에 젖을 수 있어요 |
| 5 | 직전 강수·최근 180분 누적 ≥ 1mm의 젖은 노면, 또는 신뢰 가능한 젖은 노면 CCTV 2곳 이상 | yellow / surface·surface_cctv | 노면이 젖어 있을 수 있어요 / CCTV에 젖은 노면이 보여요 |
| 6 | 선택 구간 공식 확률 또는 각 시점 현재 모델 평균 중 최댓값 ≥ 60% | yellow / probability | 비 올 가능성이 있어요 |
| 7 | 현재 시각 모델 확률 spread ≥ 40 또는 wet vote 비율 25–75% | yellow / uncertain | 예보가 엇갈려요 |
| 8 | 누적 ≤ 0.2mm이고 최대 ≤ 0.2mm/h | green / low | 눈·비 걱정 적어요 |
| 9 | 그 밖의 1mm 미만 강수 | green / light | 약한 비가 예상돼요 |

강수량은 기존 KMA·모델 현재 시각 값을 중앙값으로 섞고, 세 점을 0.25·0.5·0.25로 적분한다. 현재 시각 모델의 확률·강수량·spread·vote만 판단에 사용하며 `nextHour*`와 기존 전역 aggregate는 사용하지 않는다. 강수확률 신호는 선택 구간 공식 확률의 최댓값과 각 시점 현재 모델 평균의 최댓값 중 큰 값이다. 강수량은 기존 한 자리 반올림을 사용하되, 표시 누적량이 0이면 `light` 제목을 선택하지 않고 low·확률·불확실성 같은 판단을 선택한다. 최근 강수로 회복 중인 노면은 red가 아니라 surface yellow이며, CCTV는 `cameraUsable !== false`와 confidence `≥ 0.65`를 모두 만족할 때만 판단 근거가 된다. 이 수치는 앱의 일관된 제품 heuristic이고 기상청 특보·공식 안전 기준·의학적 판단을 대신하지 않는다.

## 옷차림

`WEAR_BANDS`, `recommendRunningWear()`는 브라우저/서버가 함께 사용할 수 있는 순수 모듈에 둔다. 가벼운 1시간 러닝 기준의 참고 추천이며 의학적 안전 판정이 아니다.

- 출발·복귀 체감온도 중 낮은 값을 사용하며 2°C 단위 반올림 없이 추천표에 대입한다.
- cold/normal/hot 선호는 추천표 입력만 -2/0/+2°C 조절한다. 화면의 실제 예보 값은 바꾸지 않는다.
- 체감에 포함된 바람 영향을 다시 차감하지 않는다.
- 판정온도 12°C 미만에서 출발·복귀 풍속 중 하나라도 4m/s 이상 또는 해당 1시간 돌풍이 8m/s 이상이면 영하에서는 보통 두께 방풍재킷, 0°C 이상에서는 얇은 바람막이를 추가한다. 이미 겉옷이 있으면 중복하지 않는다. 이 수치는 앱의 준비물 기준이며 공식 강풍특보 기준이 아니다.
- 강수량이 0보다 크면 갈아입을 옷을 안내한다. 12°C 미만이면 겉옷을 통기성 있는 방수 러닝 재킷으로 바꾸고, 따뜻한 구간은 필요에 따른 방수 겉옷 안내만 붙인다. 보온 단계를 올리지는 않는다.
- 실제 최저 체감 또는 개인 보정한 판정온도가 −10°C 미만이면 조합 대신 개인별 방한 준비 안내를 표시한다. 체감 성향으로 적용 범위를 확장하지 않으며, −10°C는 안전을 나누는 절대 기준이 아니다.
- 복귀까지 체감 자료가 없으면 추천을 만들지 않는다. 누락값을 0°C로 처리하지 않는다.
- 화면은 겉옷 → 상의 → 하의 → 양말 → 보조 순서의 행으로 표시하고, 필요 없는 행은 생략한다. 패딩 조끼는 −10~−5°C와 −5~0°C 구간의 보조 항목에 표시한다. 별도 보온조끼 추가 안내는 중복하지 않는다.
- 긴 하의 선호는 팬츠(기본)/타이즈이며 같은 보온 수준끼리 변경한다. 반바지 구간은 유지한다. `runcast.preferences.v1`에 `bottomFit`을 추가해 기존 위치·체감 선호와 함께 로컬에 저장하고, 과거 설정은 팬츠 기본값을 사용한다. 추가 API 요청은 없다.
- 옷차림 설정 아래에 사용자가 선택한 안내 이미지 `/assets/running-wear-guide.png`를 원본 그대로 표시한다. 가로폭에 맞추고 원본 비율을 유지하며, 누르면 새 창에서 크게 볼 수 있다. 크기를 미리 지정하고 지연 로딩하며 PWA 오프라인 캐시에도 포함한다. 어제 화면에서는 추천과 함께 숨긴다.

## PWA와 검증

기존 manifest의 id/start_url은 유지한다. `sw.js`는 모바일 정적 화면만 네트워크 우선 캐시하고, API와 외부 지도 요청은 가로채지 않는다. 자동 갱신 정책은 서비스 워커의 백그라운드 타이머가 아니라 포그라운드 페이지 lifecycle에서만 실행한다. 오프라인 앱 실행 시 저장된 예보를 표시할 수 있다. 향후 정적 자산 구성이 바뀌면 서비스 워커 캐시 버전을 올린다.

```sh
node --test tests/weather.test.mjs
RUNCAST_MODE=public RUNCAST_PORT=4173 node server.mjs
```

확인할 화면: 기본/사용자 위치 전환, 마지막 확정 위치·체감 재실행 복원, 초안 취소, 지도 실패 시 좌표 입력, 날짜·시간·체감 설정, 마지막 날 23시, 데이터 없음, 만료 후 조회 실패, 모바일 390px 폭.

실제 Android/iOS 기기에서 설치·재실행·오프라인 재진입과 위치 권한을 최종 확인한다. 로컬 검증은 실기기 검증을 대체하지 않는다.

러닝은 중복 요약 없이 강수 결론·3시점·판단 근거를 본문에서 표시하고, 예보 상세는 같은 자리에서 한 단계만 펼친다. 상세에는 `눈·비: 기상청`, `기온: Open-Meteo`와 각 수집·대상 시각, 시간대 매칭 기준을 구분해 표시한다. 주변 CCTV도 러닝 본문에서 거리순 링크로 제공하며, 비구름 탭의 바로가기는 같은 CCTV 구획으로 이동한다. 기상청 예보가 실패해도 CCTV·공항 context는 별도로 상태를 표시한다. 헤더의 새로고침은 활성 탭을 갱신한다. 탭별 페이지 위치, 날짜·시간 선택, 표 스크롤, 펼침과 포커스는 갱신 시 유지한다. 레이더 프레임 버튼은 응답 배열의 실제 분을 `현재`, `+10분`, `+1시간`처럼 표시하며, 선택 프레임이 실패하면 이전 영상을 남기지 않는다.
